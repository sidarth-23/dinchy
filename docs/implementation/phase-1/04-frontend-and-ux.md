# Frontend And UX

## Build And Runtime Model

Production/default mode:

- Go serves embedded frontend assets from the built Vite output
- startup verifies embed integrity before listening

Development mode:

- explicit `--dev` only
- Go proxies frontend requests to the configured dev proxy URL
- embedded assets are not required in this mode

## Router Structure

TanStack Router should be used deliberately, not as a single large-root screen.

Real routes:

- `/setup`
- `/login`
- protected app layout route
- dashboard route under the protected layout

Top-level startup states:

- HTTPS required
- setup required
- unauthenticated
- authenticated
- startup error

Startup branching is driven by the root bootstrap loader.

Rules:

- redirect to `/setup` when `setup_required = true`
- redirect to `/login` when not authenticated
- redirect to the app shell/dashboard when authenticated
- render HTTPS-required as a special top-level app state
- render startup error for unexpected bootstrap failures or invalid bootstrap invariants

## Bootstrap UX

`GET /api/bootstrap` is the canonical startup state source.

Frontend behavior:

- do one short automatic retry on transient bootstrap failure
- then show startup error screen with retry action
- do not retry policy errors such as `security.https_required`

Startup error screen:

- friendly headline
- retry action
- request ID if available
- optional expandable technical details

HTTPS-required screen:

- top-level state, not a login page
- shown globally when `security.https_required` is returned
- if configured `public_url` is HTTPS, show a secure link

## Forms

Use TanStack Form following the Shadcn integration pattern.

Setup form fields:

- `email`
- `display_name`
- `password`
- `confirm_password` client-side only

Login form fields:

- `email`
- `password`

Client validation rules are complete for UX purposes, but server validation remains authoritative for misuse and malformed requests.

Rules:

- email validated client-side and server-side
- password minimum 12 characters
- `display_name` required, min 3
- password confirmation stays client-side only; API receives one `password`

## Auth Shell And Dashboard

Authenticated shell:

- sidebar
- header
- content area

Phase 1 navigation:

- show only Dashboard
- do not expose fake future nav items yet

Dashboard content:

- empty-state card, not blank chrome
- confirms the instance is ready
- no fake metrics or placeholder product sections

## Generated Client

Phase 1 uses a generated API client from Huma/OpenAPI.

Workflow:

- OpenAPI spec generated by a dedicated Go command without starting the server
- frontend generated client output is regenerated by Taskfile commands
- generated output is not hand-edited

Frontend should still wrap the generated client in a thin API module for:

- same-origin credentials behavior
- base URL setup
- error normalization
- global `https_required` handling

## Error Presentation

Frontend and server i18n layers remain independent.

Recommended UI behavior:

- field validation errors shown inline
- backend `request.validation_failed` field data maps to form fields
- exact error-code mapping first
- namespace fallback next, like `auth.*` or `security.*`
- fallback to server message for unknown codes

## Docs UI And Browser Behavior

- docs UI is public under `/api/docs`
- same-origin cookie behavior should work naturally when the browser is logged in
- docs UI reads the CSRF cookie and sends `X-CSRF-Token` for mutating API calls

## Styling Baseline

- use the Shadcn CSS/theme baseline from the app template
- keep the theme foundation intact for later dark-mode polish
- do not add an end-user dark-mode toggle in Phase 1
